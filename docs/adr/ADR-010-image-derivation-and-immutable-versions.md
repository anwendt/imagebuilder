# ADR-010 — Image Derivation From Published Base Images and Immutable Versions

## Status

**Accepted**

---

## Context

Platforms that use ImageBuilder typically want two tiers of images, like
container registries: a small set of **base images** maintained by a platform
team, and **derived images** that other teams build on top of a pinned base image
version. ImageBuilder already has the pieces (remote builds, `spec.source`,
publishing to a provider image store), but the contract was implicit:

1. It was not stated that a `VMImage` may use the output of an earlier build as
   its source.
2. It was not stated that a published version must never change afterwards,
   which a derivation chain depends on.
3. Provider-specific connection data (credentials, placement, build folder,
   protected names) is repeated by every consumer as `ProviderConfig` content.
   Orchestration layers need a stable, documented shape to generate it.

## Decision

### 1. Derivation is a remote build with a published source

A derived image is an ordinary `VMImage` whose `spec.source` references an image
that an earlier build published to the provider's image store. The reference is
provider native and goes into `spec.source.providerRef` (type `snapshot` or the
provider's remote source form), never into a URL:

| Provider | Form of `providerRef` for a published base image |
|---|---|
| vSphere | `content-library:/<library>/<item>` or `library-item:<id>` (implemented) |
| Azure | Compute Gallery image version resource ID |
| AWS | AMI ID |
| OpenStack | Glance image UUID |
| GCP | image selfLink |

Providers that cannot start a remote build from their own published images
return `Unimplemented` for the source; the build fails closed and does not fall
back to another source.

### 2. Published versions are immutable

A provider publishes a build under a name that identifies the version. Once an
item exists it is never modified, replaced or deleted by a later build. The same
build finding its own item (identified by the build marker) is a successful
retry; any other existing item is an error. This is already enforced on vSphere
(ADR-009) and is now a contract for every provider. It makes a pinned
`providerRef` reproducible.

### 3. Lineage is reported, not trusted

A derived build reports the resolved source reference in `status` (the
`providerRef` that was actually used). Orchestrators record the base version in
their own catalog. ImageBuilder does not interpret version channels or approval
state; selecting an approved version is the caller's responsibility.

### 4. ProviderConfig is generated by orchestration layers

`ProviderConfig` remains namespaced and holds no secrets, only a Secret
reference. Layers above ImageBuilder may generate it from their own inventory
objects, owning the objects they create and never overwriting foreign ones. The
`extra` keys documented in the provider operations guide are the supported
contract; a key may be added but not renamed within a minor version.

### 5. Provisioning content lives in Git and is fetched provider-side

Scripts, Ansible roles and configuration files are not inlined in manifests.
A provisioner references them with `spec.provisioners[].source.git`
(`url`, `ref`, `path`, optional `auth.secretRef` to a read-only token). This is
already implemented: the controller or provider clones the repository
(through the configured proxy, SSRF-checked), expands a directory into ordered
steps and hands the file content to the provisioner. On vSphere the content
reaches the guest through Guest Operations, so the build VM needs neither Git
access nor credentials. The provider fetches through the ProviderConfig
`downloadProxy` when one is set (clusters that reach Git only via a proxy). Rules for orchestrators and manifests:

- `ref` is a commit SHA or an immutable tag; branches are not used for versions.
  Orchestrators resolve a tag to its commit SHA when they create the `VMImage`
  and record both (tag in an annotation), so the built version names the exact
  scripts. Changing scripts means a new tag and a new image version.
- The manifest holds only URL, ref, path and the Secret name. Smaller manifests
  keep the stored objects small and the scripts reviewable as Git diffs.
- The token is read-only and scoped to the repository.

Open engine follow-up: report the resolved commit SHA of every Git source in
`status` and refuse a branch name when a policy flag requires immutable refs.
Until then the orchestrator pins and records the SHA.

### 6. No engine change for vSphere derivation


The vSphere provider already resolves `content-library:` and `library-item:`
references for remote builds. This ADR adds no code. Two follow-ups are open and
tracked separately: a pool of build addresses (today one static address per
`ProviderConfig`) and reporting the resolved source reference in `status` for
every provider.

## Consequences

### Positive
- Base and derived images use one build engine and one resource kind.
- Orchestrators can rely on immutable versions and a stable `ProviderConfig`.

### Negative
- Derivation needs a provider with a remote build path; local builds do not
  support it.
- The immutability contract cannot be enforced by providers whose image store
  allows overwriting by the same name; those must use unique names.
